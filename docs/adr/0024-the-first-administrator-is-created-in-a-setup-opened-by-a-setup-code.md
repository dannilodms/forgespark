# The first administrator is created in a setup opened by a setup code

ADR-0011 lets in registered users only, and it took the e-mail of the first user from the deploy configuration. That left a new install with a user and no consultancy, and it put a person's e-mail among the deploy variables. The terms setup, setup code and administrator are in `GLOSSARY.md`.

A new install has no user and no consultancy. Whoever installs it issues a setup code with a command of the API binary, run in the container, and types it on the setup screen. The setup registers the consultancy and its first administrator.

- **The setup code is not a user.** It opens the setup and nothing else: it gives no session and reaches no other operation. No user name and no password exist for it, so the system still stores no password.
- **Typed, never in an address.** The command prints the code and the person types it on the screen, so it stays out of the browser history, the logs and the spans. The screen keeps it in memory only and sends it in the body of each request of the setup. A page loaded again asks for it again.
- **Long, random and stored as a hash.** The code has 20 letters and digits in four groups, with no character that reads like another: about 100 bits. Only its SHA-256 hash is stored. It lasts one hour, and issuing a new one ends the one before.
- **A wrong code ends nothing.** The code cannot be guessed, so the only limit on checking it is the one Caddy sets for each IP address. Nobody outside can end a setup code by typing wrong ones.
- **The setup is the only screen until it is concluded.** Every address of the app leads to it, and nobody can log in. Afterwards the address of the setup leads to the login screen, except while a setup code is issued and still valid.
- **Created together.** The consultancy, the administrator and the two first roles (ADR-0026) are saved in one operation when the setup is concluded, and the setup code stops working then. Before that nothing of them is saved, and the same code opens the setup again.
- **No session from the setup.** Concluding leads to the login screen, and the administrator logs in as ADR-0011 describes. An e-mail typed wrong shows while the person who installed is still at the server.
- **A way back in.** When no administrator can log in, a new setup code, issued by the same command, opens the setup at the step of the administrator and registers a new one. The command says which of the two setups the code opens. The users that exist are left as they are, so an e-mail that already belongs to a user is refused.
- **Administrators register the other users.** ADR-0011 said any existing user did.

## Considered Options

- **The e-mail of the first user in the deploy configuration.** The earlier decision. No screen and no code, but the first login would find no consultancy, a person's e-mail would sit among the deploy variables, and changing it would take a deploy.
- **A super administrator with a password generated by the command.** Familiar from other self-hosted systems, but it is a stored password, a second login form, and a user to disable once the setup is done.
- **A super administrator who logs in through the login screen, with a code issued by the command.** No password, but a user that is not a person stays among the users.
- **A link that carries the setup code.** One step fewer, but the code would stay in the browser history and in the logs.
- **Saving each step.** A browser closed halfway would leave a consultancy with no administrator.
- **Concluding logs the administrator in.** Fewer steps, but an e-mail typed wrong would show only at the next login.
- **A command that registers an administrator by e-mail, to get back in.** No screen, but a second way of creating an administrator, without the data the setup asks for.
- **Confirming the e-mail with a login code before concluding.** It catches a typing mistake but not a mailbox lost later, and the setup would depend on the e-mail server.
- **A shorter code, or six digits like the login code.** Easier to type. Twelve characters would lean on the limit against guessing, and six digits cannot be stored as a hash.
- **A setup code ended by a few wrong attempts.** The rule of the login code. Anyone who reached the address could end the code of whoever is installing, again and again.
- **The address of the setup always showing the field for the code, or a link to it on the login screen.** Neither tells whether a code is issued, but the field would be open to anyone at all times.
- **The way back in giving the administrator role to an existing user.** It would promote a developer in one step. The setup would then change a user it did not create, with data typed by whoever holds the code.

## Consequences

- The API needs operations that work with no session: one that tells whether the setup is concluded, and the ones of the setup, allowed by the setup code alone.
- Checking a setup code has a limit against guessing: Caddy limits it for each IP address, together with the operations of the login code (ADR-0011). ADR-0009 lists it as the second limit of the API.
- While a setup code is issued and still valid, the operation that tells whether the setup is concluded also tells that a code is waiting. Someone outside learns that much and nothing else.
- The images chosen in the setup are sent before any user exists, so their signed URLs (ADR-0017) are issued under the setup code. An image sent and never used is removed like any upload that was never confirmed.
- Concluding the setup and registering an administrator confirm the images they were given, which reads the storage, before their transaction. So each first checks every field, then the setup code and whether the setup is concluded, without a lock, and only then confirms the images: a wrong code, or a code used on the wrong operation, never makes the API read or remove an object. The transaction then locks the setup code and checks both again, since the code may end, or the setup be concluded, between the two checks.
- The seed creates a consultancy and an administrator through the use cases (ADR-0019), so development and staging open on the login screen. The setup has tests of its own.
- The deploy configuration loses the variable with the e-mail of the first user.
- Whoever can run a command in the container can become an administrator. That was already true of whoever can reach the database.
- Issuing a setup code and concluding a setup are sensitive operations, so each writes to the audit log (ADR-0012).
