# 08 - First screen: the gate of the setup and the step of the setup code

Status: ready-for-agent
Blocked by: 06, 07

Read `../spec.md`, `DESIGN.md` and the frontend rules of `CODING_STANDARDS.md` first. The reasons are in ADR-0013, ADR-0014 and ADR-0025. The layout follows the login screen of the removed prototype, described in `.scratch/login-screen-prototype/spec.md` at commit `cc48eb1`.

## What to build

A new install shows only the setup screen. The person types the setup code and gets past the first step. This is the first screen built against the API, so it also sets how a screen, its data module and its tests are written.

- The client, the Zod schemas and the simulated responses generated by orval from the committed spec, committed, with a check that fails when they are stale.
- The `consultancy` area of `apps/web`, with the setup screen and a data module that exposes the reads and writes of the setup under glossary names. The state of the setup is read through TanStack Query. Only the data module uses the generated client.
- The `access` area, with a provisional login screen: it says the login is not built yet, and shows a notice that the setup is concluded when the person arrives from it. The second effort replaces it.
- The gate. Until the setup is concluded every address leads to the setup. Afterwards the address of the setup leads to the login screen, except while a setup code is waiting, and every other address leads to the login screen.
- The setup screen as one route whose state is a union of named steps in one reducer. This ticket builds the step of the code and leaves the next step as a placeholder that says which setup the code opened.
- The frame of the screen: a title bar with the product name, a status bar that holds the language selector and nothing else, and one bordered pane in the centre of a page with the page framing of `DESIGN.md`. At a narrow width the pane takes the width of the page.
- The step of the code: one field, one primary button. A code that is not valid shows one message that says to issue a new one. The limit reached shows a message that says to wait.
- The translation of an API error by its `code` and `params`, in the language of the screen, showing its `trace_id`. A failure while rendering falls to an error screen that offers a reload.
- The language of the screen starts as the language of the browser, or English when it is not supported, and the selector changes it at once.
- Every text in the three supported languages, in the translation files of its area.
- Screen tests in Vitest's Browser Mode, with the API simulated by MSW from the generated responses.
- Knip, and the check of the dependency rule of the frontend, whose tool is chosen here. Both run in `task check`.
- A job for the app in `ci.yml`, added to the `needs` of `Checks`.
- `CODING_STANDARDS.md` records the tools chosen.

## Acceptance criteria

- [ ] With the setup not concluded, the root address and any other address show the setup screen.
- [ ] With the setup concluded and no setup code waiting, the address of the setup shows the login screen. With a setup code waiting, it shows the step of the code.
- [ ] A valid code moves to the next step, which says whether the code opened the first setup or the registration of a new administrator.
- [ ] A code that is not valid shows the message on the field and keeps what was typed. The limit reached shows its own message.
- [ ] The code is held in memory only: it is in no address and in no browser storage, and a page loaded again asks for it again.
- [ ] An error that the screen does not expect shows a translated message with its `trace_id`.
- [ ] The language selector changes every text without a reload. The missing-key check passes for the three languages.
- [ ] Correct in light and dark, at desktop width and at 375px, with no overflow, and fully operable by keyboard.
- [ ] The screen tests act as a person does and cover each route before and after the setup, a valid code, a code that is not valid and the limit reached.
- [ ] A stale client, an unused file, export or dependency, and an import that breaks the dependency rule each fail `task check`.
- [ ] The job of the app runs on a pull request and the `Checks` job needs it.
- [ ] orval works on the spec Huma generates. What had to be adjusted is noted in ADR-0013.
