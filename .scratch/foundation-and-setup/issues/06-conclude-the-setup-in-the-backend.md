# 06 - Conclude the setup in the backend

Status: ready-for-agent
Blocked by: 05

Read `../spec.md`, ADR-0024, ADR-0026 and, in `CODING_STANDARDS.md`, Setup, Users and roles, Domain modelling and API conventions. The terms consultancy, user, role, administrator, developer, tax ID and national ID are in `GLOSSARY.md`.

## What to build

A caller with a valid setup code registers the consultancy and its first administrator in one operation, and anyone can ask whether the setup is concluded. Images come in ticket 10.

- The consultancy, the user and the role as aggregates of the `consultancy` area, with the tables "Database" in `../spec.md` describes. The database refuses a second consultancy and a second user with the same e-mail.
- The domain rules of `../spec.md`: the required fields of each; the country, the currency and the time zone checked against lists the backend carries; the tax ID and the national ID as free text within a length limit; the e-mail lowered; the telephone in international form; the website as an `http` or `https` address; the preferred language as a supported language. The value objects that more than one area will use go to `kernel`.
- The use case that concludes the setup. It validates everything first. Then, in one transaction, it locks the setup code, checks that it is valid and that no consultancy exists, creates the administrator role and the developer role, the consultancy and the administrator with the administrator role, ends the setup code and writes to the audit log. The actor of the entry is the setup code used, and its subject is the user created.
- `POST /api/setup/conclude`, with the setup code and the data in the body, answering 204. A code that is not valid answers `setup_code_invalid`; a consultancy that already exists answers 409 with `setup_already_concluded`; a failed validation answers 422 and names the field.
- The query that tells the state of the setup, and `GET /api/setup`: whether the setup is concluded and whether a setup code is waiting. It needs no session.
- The use case that opens the setup now answers from the real state.

No scope exists yet, so no table links a role to its scopes. The administrator role stores none.

## Acceptance criteria

- [x] With valid data and a valid code, the consultancy, the administrator, the two roles and the audit entry exist afterwards, the administrator holds the administrator role, and the setup code is ended.
- [x] The developer role exists and no user holds it.
- [x] `GET /api/setup` says not concluded before and concluded after, and says a setup code is waiting only while one is issued and still valid.
- [x] Each required field missing, a country, a currency, a time zone or a language outside its list, a malformed e-mail, telephone or website, and an identifier over the length limit each answer 422 naming the field, and save nothing.
- [x] An e-mail typed in upper case is stored in lowercase.
- [x] Concluding twice with the same code saves once: the second attempt answers `setup_code_invalid`.
- [x] Two concluding requests at the same moment save one consultancy. A test against PostgreSQL proves it.
- [x] A failure at any point of the transaction leaves no consultancy, no user, no role and a setup code that still works.
- [x] No e-mail, name or identifier of a person appears in a log line, a span or the audit entry. The test of sensitive values guards them.
- [x] The business rules are tested through the use case with in-memory implementations, and the spec, the generated code and the lint are up to date.

## Comments

### What was built

- **The aggregates**, in `apps/api/internal/consultancy/domain`: the consultancy (`consultancy.go`), the user (`user.go`) and the role (`role.go`). Each is created from details checked first (`NewConsultancyDetails`, `NewUserDetails`), so a use case validates before it reserves an identifier. A user is never without a role. A role carries the fixed key `administrator` or `developer` and no scope.
- **The value objects of `kernel`**: `Country`, `Currency` and `TimeZone` (`places.go`), each checked against a list the backend carries; `Language`, the supported language; `Email`, lowered; `Telephone`, a plus sign and 7 to 15 digits, stored without spaces; `Website`, an http or https address with a host. `RequiredText` and `OptionalText` trim a text and check its length in characters. Each broken rule is a typed error with its stable code.
- **The lists**: `countries.go` (249 codes, ISO 3166-1 alpha-2 from Debian's iso-codes v4.20.1), `currencies.go` (155 codes, ISO 4217 from the same release, without funds, metals and units of account) and `time_zones.go` (597 names, every zone and link of the IANA tzdata 2026c that Go 1.27.4 carries). Each file names its source and how to update it.
- **The rule about a field**: `kernel.InvalidFieldsError` lists every field that breaks a rule, named as the input is structured (`consultancy.address.city`). `restapi.InField` declares a rule under 422, and the answer is `validation_failed` with one entry in `errors` for each field, at `body.<field>`, with the code of the rule and its parameters.
- **The use cases**: `ConcludeSetup` validates everything, then in one transaction locks the setup code (`LoadByHash`, `SELECT ... FOR UPDATE`), checks that it works and that no consultancy exists, creates the two roles, the consultancy and the administrator with the administrator role, ends the code and records `setup_concluded` in the audit log, with the setup code as actor and the user as subject. `TellSetupState` reads whether the setup is concluded and whether a code is waiting. `OpenSetup` answers `first_setup` or `new_administrator` from whether the consultancy exists.
- **The tables**: migration 00004 creates `consultancy` (one row at most, by a unique index on `(true)`), `roles` (unique key), `users` (unique e-mail; the preferred language has no `CHECK`, so a new language never changes the schema) and `user_roles`, with the rights of the API role. Migration 00005 adds the values of the conclusion to the `CHECK` constraints of the audit log.
- **The `postgres` adapters** of the consultancy, the users, the roles and the state of the setup, with their SQL and the code sqlc generated.
- **The operations**: `GET /api/setup` (`tell_setup_state`, 200 with `concluded` and `setup_code_waiting`) and `POST /api/setup/conclude` (`conclude_setup`, 204; 422 `setup_code_invalid`; 409 `setup_already_concluded`; 422 `validation_failed`). The bodies take their limits and forms from the domain in `TransformSchema`, and `preferred_language` is an `enum` of the supported languages.
- **The 429 of Caddy in the spec**, asked by the orchestrator after ticket 07 merged: `restapi.LimitedByCaddy` lists `too_many_requests` under 429, in the error format, on `open_setup` and `conclude_setup`, so the client and the simulated responses of ticket 08 know it. No use case returns it.
- **The test of sensitive values**: the scenario with PostgreSQL out of reach now concludes a setup with the name, the e-mail and the national ID of a person, and a new scenario concludes it on a migrated database through every way it can go, searching the logs, the spans, the answers and the audit log.
- **The documents**: `CODING_STANDARDS.md`, in Errors (the rule about a field, `InField`, the codes of `errors`, what the contract checks first), Between domain areas (`kernel` holds that error) and Values (the lists in `kernel`).

### Decided while building

- **Which value objects went to `kernel`**: the country, the currency, the time zone, the language, the e-mail, the telephone and the website. Each is a general form, and the clients, the e-mails and the login will use them. The tax ID and the national ID stay plain text in the domain of the area, as free text within a limit.
- **The length limits**: 200 characters for a name and a legal name, 50 for a tax ID and a national ID, 200 for a line of the address, 100 for the city and the region, 20 for the postal code, 254 for an e-mail (RFC 5321) and 2048 for a website. Counted in characters.
- **Every text is trimmed** of the spaces around it, and otherwise stored as typed. A required text of spaces only is `required`.
- **The telephone** accepts spaces only as separators: a hyphen or a parenthesis is refused, as "a plus sign and digits" reads. 7 to 15 digits, the shortest international numbers and the E.164 limit.
- **The currencies are those in circulation.** A consultancy does not charge in gold or in a unit of account, and the list a screen builds from it should not offer them.
- **The time zones include the links**, so the older name a browser may report is accepted.
- **The lists are not in the contract**, except the languages. An `enum` of 600 time zones would fill the spec and every message of a refused value, and the code of the list (`country_unknown`) says more than `invalid`. The contract declares what a client can check before it sends: required texts with at least one character, the lengths, the form of an e-mail, of a telephone and of a website. The body types take them from the domain constants, so the two cannot drift.
- **An empty text where the contract asks one character is `required`**, like a missing property, and a field is named once, for the first rule it breaks.
- **The fields are checked before the setup code.** A body with a wrong code and an empty name answers the field first.
- **The lock is on the setup code.** Two concluding requests with the same code run one after the other, and the second finds the code ended: `setup_code_invalid`, as concluding twice is. The unique index of the consultancy is the last guard.
- **Opening the setup answers from the real state**, so `new_administrator` entered the domain and the `enum` of `OpenedSetup` now. Issuing a code still says `first_setup` always: the command is ticket 12's.
- **`GET /api/setup` lists 500** under its failures, as the other operations do, instead of Huma's `default`.
- **No load of a consultancy, a user or a role** is written: nothing reads them yet.

### Found, and left for a decision

- **Two lists of supported languages.** ADR-0005 speaks of a single list. The backend checks the preferred language against `kernel.supportedLanguages`, beside `apps/web/src/shared/locales/languages.ts`. The contract exposes the backend's list as the `enum` of `preferred_language`, so ticket 08 can derive the frontend's from the generated client, or check that the two agree.
- **The list of countries for the screen.** The browser has no list of regions. Ticket 09 needs one, and the one the backend accepts is `kernel/countries.go`.
