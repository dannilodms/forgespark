# 03: Asking for a login code

**What to build:** A person sends their e-mail to the API and, when it belongs to an active user, a six-digit login code reaches their mailbox within seconds, in their preferred language. The answer is the same for every e-mail, and nothing of the code is stored anywhere. The browser that asked is remembered in a session that exists before any login. Rules: Login and Rate limit in `CODING_STANDARDS.md`, ADR-0011. Verifiable with `curl` and Mailpit.

**Blocked by:** 02 (E-mail records sent through SMTP).

**Status:** resolved

- [x] The session exists before the login: `alexedwards/scs/v2` with `pgxstore`, its table from a migration, an opaque `HttpOnly` `SameSite=Lax` cookie (`Secure` off in development), idle life 7 days, absolute life 30 days.
- [x] A `POST` that takes the e-mail answers 202 with no body for every e-mail. For an active user it ends their open requests, saves a login code request (identifier, user, random value, asked at, expires at, attempts, ended at) and queues the e-mail with its job in one transaction, and stores the request's identifier in the session. For an unknown or deactivated e-mail nothing is saved.
- [x] The code is HMAC-SHA256 of the request's identifier and random value under a key from configuration, reduced to six digits; the delivery computes it to write the e-mail. It is in no table, job argument, log or span, and the test of the logs proves it.
- [x] One request a minute and five an hour for each user, counted on their requests; past them the operation answers 422 with a rule of its own.
- [x] A new request ends the one before it.
- [x] Use case tests cover a known, an unknown and a deactivated e-mail with the same answer, the two limits with a fixed clock, and the ending of the earlier request.
- [x] The `postgres` adapter tests cover the session store and the requests with their counts.
- [x] Caddy has a zone `login` of 10 requests a minute for each IP address over the two operations of the login code, asking and checking (the path of checking is reserved here and built in 04), separate from the zone of the setup; `caddy_test.go` reads the 429 in the error format; the numbers go to Rate limit in `CODING_STANDARDS.md`.
- [x] In development, asking with `curl` through Caddy puts an e-mail with the code in Mailpit.

## Comments

### What was built

- The domain area `access` (`apps/api/internal/access`):

  - `application`: `AskForLoginCode` (with `LoginCodeDependencies`, which ticket 04's check can share), `LoginCodeContents` (the `ContentSource` of the template `login_code`), the interfaces `LoginCodeRequestRepository` and `Session`, and the in-memory implementations in `applicationtest` (a session per browser, `InBrowser(ctx, browser)`).
  - `adapters/postgres`: `LoginCodeRequestRepository` on the table `login_code_requests` (migration `00018`, sqlc entry).
  - `adapters/rest`: the operation `ask_for_login_code`, `POST /api/session/login_code`, 202 with no body, and `Session`, which keeps the request in the session of the browser.
- `platform/session`: scs v2.9.0 with pgxstore on the pool; table `sessions` from migration `00017`. Cookie `session`, HttpOnly, SameSite=Lax, Path=/, persistent, Secure when `APP_ORIGIN` is https; idle life 7 days, absolute life 30 days; the table keeps the SHA-256 of each token (`HashTokenInStore`). `Under(restapi.Prefix, mux)` loads and saves the session of the requests under `/api` only. Its cleanup stops in `serve` before the pool closes.
- `consultancy`: the query use case `FindActiveUser` (the active user of an e-mail, with their identifier, e-mail and preferred language; a deactivated user is not found), with `ActiveUserReader` in `postgres` and in `applicationtest` (plus `RegisterUser` and `DeactivateUser` there, for the tests of another area).

- Commands: `serve` builds the saver of jobs and the sessions; `mountREST(mux, served{pool, storage, saver, sessions})`, which the spec test calls with `served{}`. `mountJobs` wires `LoginCodeContents` as the content of the login code, and returns an error now.

### Decided while building

- **The paths.** The login lives under the session of the browser, a resource that exists once for each browser: `POST /api/session/login_code` creates the login code of the session (202: its e-mail leaves through a job), and checking it is `POST /api/session/login_code/check` (ADR-0009: a state change ends in the verb of its use case). `/api/session` and `/api/session/login_code` join the singular paths of the lint. `caddy_test.go` now posts to `/api/session/log_out`, a path of the session outside the zone, where it posted to `/api/sessions`.
- **The e-mail value object moved to `kernel`**, as the orchestrator decided, with `TooLongError` (the rule of a text too long for its field), which `NewEmail` answers, so a too long e-mail keeps its code `too_long` in the setup. `RequiredText` stays in `consultancy`. Between domain areas in `CODING_STANDARDS.md` says so.
- **The user is found through a use case of `consultancy`** (`FindActiveUser`), as Between domain areas asks: `access` holds the user by identifier and never reads `users` itself.
- **The session is written the same way for every e-mail.** An e-mail of no active user keeps `NoLoginCodeRequest` (0) in the session: otherwise the answer for a user would set a cookie and the answer for anyone else would not. A refused request (the limit, a field) changes nothing in the session. The check of 04 reads 0 as no request.
- **The session is written after the transaction commits**, so a request that was not saved is never kept. A use case reaches the session through `Session`, which the `rest` adapter implements on `platform/session`.
- **The request is locked before it is counted.** `LoadNotEndedOf` locks the open request of the user, then the limits are counted, so two requests of one user at once are counted one after the other. A partial unique index keeps one open request per user.
- **The `Secure` attribute follows `APP_ORIGIN`** (https → Secure) instead of a variable of its own, so production cannot leave it off by mistake. The API now requires `APP_ORIGIN`, which ticket 04 needs for the check of the origin anyway.
- **The table keeps the hash of the token** (`HashTokenInStore`): a dump of the database opens no session.
- **Only `/api` loads a session.** Liveness and readiness must touch no part, and a session cookie on them would query the store. `Under` writes the route the mux matched back on the request the telemetry reads, because scs hands the mux a copy of the request.
- **The key is required by the worker only**: the API does not compute a code before 04, which adds it to `ServeAPI`.
- **The delivery gives the code whether or not its request still works**: the e-mail leaves within seconds, and a code that no longer works is refused at the check.
- **pgxstore** has no tagged release; it is pinned at the pseudo-version of its last commit (`v0.0.0-20251002162104-209de6e426de`), which `task versions:check` accepts.

### Found, and left for a decision

- **The limit tells a user from anyone else.** A second ask within a minute answers 422 `login_code_limit_reached` for the e-mail of an active user, and 202 for any other e-mail, so whoever asks twice learns whether an address belongs to a user, against "the same answer for every e-mail". The spec decided the 422 on the requests of the user; Caddy's 10 a minute for each IP address slows a sweep but does not stop it. Ways out: answer 202 past the limit too and send nothing (the screen then cannot say "wait"; it could say it on its own after a second ask within a minute), or count every e-mail typed, which stores addresses of people who are not users.
- **The time of the answer.** For a user the API runs a transaction of a few statements, for anyone else one read: the difference is milliseconds and was not measured. ADR-0011 moved only the sending to a job.
- **Two asks of one user at the same instant**, when the user has no open request, both pass the count and the second insert breaks the unique index of open requests: that request answers 500 (rare: a double click lands in the same milliseconds only by chance).
- **The login code requests are never removed.** Only the last hour counts and only the open one works; a periodic job could remove the older ones, as the cleanup of the storage does for uploads.
- **The cleanup of pgxstore** writes a failure with Go's standard logger (a plain line, not JSON) and runs its `DELETE` every five minutes outside any request (a span of its own each time). Writing the cleanup in `platform/session`, with the logger and no span, is a few lines if the maintainer wants the rule of JSON lines to hold there too.
- **The development database is now at migration 23 and seeded** (the check with `curl`), with this ticket's 00017 and 00018 applied before the merge. If this branch were not merged, that database would hold two migrations no other branch has (`task db:clean` does not touch it; a new volume would).

### Settled at the end of the effort

- **The limit told a user from anyone else**: decided by the maintainer and fixed in the review-fix pass. The limits count the asks for the typed address, whoever it belongs to, kept as an HMAC of the address under a key derived from the key of the login code for one hour (`login_code_asks`, migration `00026`), so every address meets the same 422. Recorded in ADR-0011 and in Login of `CODING_STANDARDS.md`.
- **The time of the answer**: narrowed by the same fix, since every ask now runs one transaction that counts it; the gap that remains (a known address also saves the request, the e-mail and the job) is recorded as known in ADR-0011, with no delay added and nothing measured, as the maintainer decided.
- **Two asks of one user at the same instant**: fixed in the review-fix pass. The ask takes an advisory lock keyed by the address first, so the second waits, counts the first and answers the limit; the tests of the `postgres` adapter prove the wait, and a test of the binary sends two asks at once (one 202, one 422, never a 500).
- **The login code requests were never removed**: decided by the maintainer and built in the review-fix pass. The daily cleanup of the worker removes them a day after they ended or expired (migration `00027` lets the API role delete them). Recorded in Jobs of `CODING_STANDARDS.md` and in ADR-0016.
- **The cleanup of pgxstore**: decided by the maintainer and built in the review-fix pass. pgxstore runs no cleanup (an interval of zero), so it writes no plain line and opens no span; the daily cleanup removes the sessions that ended. Recorded in Database and Jobs of `CODING_STANDARDS.md` and in ADR-0016.
- **The development database at migration 23**: no longer open; it is at 25 with the effort merged, and the review-fix pass adds `00026` and `00027`.
- **pgxstore at a pseudo-version**: accepted as it is, since pgxstore has no tagged release and `task versions:check` accepts the pseudo-version.
