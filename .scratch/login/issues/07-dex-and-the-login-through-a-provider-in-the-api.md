# 07: Dex and the login through a provider in the API

**What to build:** A person navigates to the operation that starts a login through the local login provider, authenticates at Dex, and comes back logged in with the same session the login code gives. The first login is matched by verified e-mail and leaves a provider link; later logins use the link. A verified e-mail of no active user comes back refused, with the e-mail kept in the session for the screen to show. A read that needs no session tells which providers are on and the last refusal. Rules: Login in `CODING_STANDARDS.md`, ADR-0011. Verifiable by navigating the browser to the start URL and reading who am I afterwards.

**Blocked by:** 04 (Checking the code: the session, who is acting, logging out and the origin).

**Status:** resolved

- [x] Dex is a service of the development Compose file only, published on a port of the machine so the browser and the API binary reach the same issuer URL; its configuration file has one static client and two people with fixed passwords, the administrator and the developer of the seed at the default mailbox (`<local part>+admin@` and `<local part>+developer@` of the fictitious default of 09).
- [x] A login provider is a set of configuration variables: issuer URL, client identifier, client secret, display name and key; the local one is on when they are set and off when empty. When on, a log line at the start of the API names it.
- [x] The `oidc` adapter does discovery, the authorization code flow with PKCE, `state` and `nonce`, and validates the ID token with `coreos/go-oidc/v3`, taking the e-mail only when the token says it is verified; its test runs against the Dex container, driving Dex's login page over HTTP.
- [x] The start operation is a `GET` with the provider key in the path and the return path as a query parameter; it stores state, nonce, verifier and return path in the session and redirects to the provider.
- [x] The callback is a `GET` with the key in the path: it checks the state, exchanges the code, validates the token and the nonce, finds the provider link by provider and subject or else the active user with that verified e-mail and creates the link, logs the user in, writes `logged_in` with the provider key as the way in, and redirects to the return path when it is a path of the app, or to the root.
- [x] A verified e-mail of no active user (unknown or deactivated) stores the refusal with the e-mail in the session and redirects to the login with `notice=no_active_user`; an unverified e-mail, a cancel or an error at the provider redirects with `notice=login_not_concluded`; a wrong state logs nobody in.
- [x] A provider link is a row of provider key, subject and user, unique on provider and subject; the `postgres` test proves the uniqueness.
- [x] A read that needs no session answers the login state: the providers turned on with key and display name, and the e-mail of the last refusal in this browser when there is one.
- [x] Use case tests cover the match by link, by verified e-mail, the link created once, the refusals, and the audit entry; HTTP tests by the binary cover the redirects and that no token or e-mail appears in a path, query parameter or header of the spec.
- [x] Both operations are in the contract as operations that answer a redirect, and the lint of the spec passes.

### Decided while building

- **Paths, under the session.** The login state is `GET /api/session/login` (`tell_login_state`), the login of the session before anyone is logged in. The start and the callback are `GET /api/session/login_providers/{key}/start` and `/callback`: they stay under `/api/session` because they write its session, and are **carved out explicitly** of the rule of `openapi_test.go` that no path under `/api/session` takes a parameter. A test of their own, `TestTheLoginThroughAProviderTakesTheKeyInItsPathAndNoEmailOrToken`, asserts the exact parameters of each (the key in the path; `return_to`; `code`, `state`, `error` and `error_description`), no header, and the redirect with its `Location`. The plural-path lint lists both paths, a `GET` that ends in what it does, which the rule allows a `POST` alone; Paths in API conventions says so.
- **The callback refuses no query parameter**, because the provider writes it (Google adds `authuser` and `prompt`, Microsoft `session_state`): it is registered with `SkipValidateParams`, the one exception, recorded in Input of API conventions. Huma still declares a 422 for it, which it never answers.
- **Every login through a provider asks for a verified e-mail**, the account linked or not (user story 10), and **a user has one link at each provider** (`UNIQUE (provider_key, user_id)`, as the glossary says): another account of that provider claiming the e-mail of a linked user logs nobody in, with `login_not_concluded`, so an e-mail that changes hands at the provider never logs someone else in (user story 12). ADR-0011 records both.
- **The e-mail of a refusal is the one the token gave**, also for an account linked to a user deactivated since, who is refused as an unknown e-mail is. The outcome of the next callback replaces the refusal (kept for `no_active_user`, forgotten otherwise) and any login forgets it; the start leaves it, and reading the state forgets nothing.
- **The login in progress is used once.** The callback takes it from the session before anything else, whatever comes of it: a forged callback uses up the login it pretends to conclude, and the browser's own callback then logs nobody in.
- **Where the browser goes.** The start answers 302 to the provider, or to `/login?notice=login_not_concluded` when the provider cannot be reached, with nothing written to the session. The callback answers 303 to the path to return to, or to `/login?notice=no_active_user` or `?notice=login_not_concluded`; both keep `return_to` when it is not the root, so a new attempt from the button of ticket 08 returns there too. A key of no provider turned on answers 404 `not_found` in the error format. A failure of the system, such as the database, answers 500 in the error format, as everywhere.
- **The provider is discovered at its first login**, not when the API starts, so the API starts while Dex is down, and a failed discovery is tried again at the next login. go-oidc fetches the keys of the provider on a background context of its own, so those calls are spans of a trace of their own.
- **The adapter logs its failures itself**, at `warn`: the use case turns them into a notice, so no 5xx line carries them. The text names the step, the status and the OAuth code of the answer, never the description or the body the provider wrote, and keeps their first line and 200 characters.
- **The configuration of Dex reads the variables of the API** (the client identifier, its secret, the key) and `DEX_PORT`, so each value is written once; its issuer is `http://localhost:${DEX_PORT}`, which `LOCAL_LOGIN_PROVIDER_ISSUER_URL` repeats, as `.env.example` says. The dollar signs of the bcrypt hashes are doubled for Compose.
- **The display name in `.env.example` is "Local login provider"**, what the button of ticket 08 shows.

### Found, and left for a decision

- **The development database is at migration 25**, applied from this worktree for the check with `curl`, and holds a provider link of Ana and a `logged_in` with the way in `local`. Until this branch is merged, the API of another checkout on that database is not ready and its worker refuses to start, and a ticket running in parallel must not take 00025.
- **A person who lost the account linked at a provider** (a new account at Google with the same e-mail, say) is refused there with `login_not_concluded`, and nothing removes a link: the API role cannot delete one, and no use case does. They log in with a login code or through another provider. A use case to unlink, with the user's settings, would be the way out; a notice of its own, telling why, is another.
- **Two first logins of one account at the same instant** both find no link, and the second breaks the primary key of `provider_links` and answers 500 (rare: two callbacks of one account within milliseconds).
- **The spec of the callback declares a 422** (Huma adds it to an operation with parameters) that it never answers, since it skips the check of its parameters.
- **go-oidc fetches the keys of the provider in a goroutine of its own**, on a background context, bounded by the timeout of the client (10 s): a library that does not follow "no goroutine outlives its request" to the letter.
- **A provider that writes `email_verified` as a text** (`"true"`, as some do) fails the reading of the claims and logs nobody in. Each provider is checked when it is configured, as ADR-0011 already says.
- **A login started and never concluded** stays in the session until the next start replaces it or the session ends; it has no time limit of its own, besides the code at the provider, which expires.

### Settled at the end of the effort

- **A person who lost the account linked at a provider**: unlinking deferred by the maintainer to the users effort (Deferred in `CODING_STANDARDS.md`). The review-fix pass gives the case its own notice: the callback redirects to `/login?notice=another_account_linked`, and the login screen says the account is not the one linked to the user and to use that account or a login code, in the three languages (story 17). Recorded in Through a provider of Login in `CODING_STANDARDS.md` and in ADR-0011.
- **Two first logins of one account at the same instant**: fixed in the review-fix pass. The link is inserted with `ON CONFLICT DO NOTHING`; the second login waits for the first, saves nothing, reads the link again in its own transaction and logs the same user in. Tested at the `postgres` seam and on the use case. Recorded in Through a provider.
- **The 422 the callback declared**: fixed in the review-fix pass. An operation that checks neither its parameters nor a body, and declares no broken rule under 422, no longer declares it (`restapi.Register`); the callback skips the check of its body as well, and a test of the spec says so.
- **go-oidc fetches the keys in a goroutine of its own**, bounded by the timeout of its client: accepted as it is, a library that holds nothing of a request. The review-fix pass also takes the lock off the discovery: a provider that hangs keeps waiting only the login that called it.
- **A provider that writes `email_verified` as a text**: deferred by the maintainer to the deploy effort, which checks each real provider as it is configured. Recorded in ADR-0011 and under Deferred.
- **A login through a provider has no time limit of its own**: accepted by the maintainer. Recorded in ADR-0011 and in Through a provider.
- **The development database at migration 25**: no longer open.
