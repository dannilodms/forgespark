# 04: Checking the code: the session, who is acting, logging out and the origin

**What to build:** The six digits typed in the browser that asked for them log the user in. From then on every request under the contract knows who is acting, with the scopes of their roles; the user can ask who they are and log out; a deactivated user is refused and their session ends; a request that changes state from another origin is refused; and the login is written to the audit log. Rules: Login and Users and roles in `CODING_STANDARDS.md`, ADR-0011, ADR-0012, ADR-0026. Verifiable with `curl`: code, cookie, who am I, log out.

**Blocked by:** 03 (Asking for a login code).

**Status:** resolved

- [x] A `POST` takes the six digits and reads the request's identifier from the session. No request in this browser, a request ended or expired, or a wrong code answer the same rule, "the code is not valid", with the attempts left; the comparison is in constant time.
- [x] The third wrong attempt ends the request and answers that the code ended; a right code ends the request, renews the session token and stores the user's identifier.
- [x] The REST adapter reads the session on every operation that needs a user, loads the user and their roles, and passes an actor with the user's identifier and the scopes of their roles: every scope for the administrator role, none for the developer role. A missing session answers 401; a deactivated or missing user gets 401 and their session destroyed.
- [x] An operation answers the logged-in user: name, e-mail, preferred language and the keys of the roles (the photo URL arrives in 06).
- [x] A named `POST` operation on the session logs out and destroys the session.
- [x] A `POST` or `PUT` with the session cookie is refused with 403 in the error format when `Origin` is present and differs from the app origin, or when `Origin` is absent and `Sec-Fetch-Site` is `cross-site`; a request with no cookie is not checked.
- [x] The audit log gains the actor kind `user` and the operation `logged_in`, with a new column for the way in (`login_code` here, the provider key later); the CHECK constraints grow with them, and the `postgres` test shows the table still refuses updates and deletes.
- [x] Use case tests cover a right code, a wrong one three times, an expired one, one from another browser, the audit entry, who is logged in and the logout; a fixed clock drives expiry.
- [x] HTTP tests by the binary cover the cookie and its attributes, 401 without a session and after deactivation, the 403 on a cross-origin `POST`, and that no code, e-mail or token appears in any path, query parameter or header of the spec.
- [x] The test of the logs covers the session cookie.

### Decided while building

- **The actor in `kernel`** holds the user as an `int64`: `kernel` names no type of an area, and each area turns it into its own identifier. The list of scopes lives beside it, empty; what a role grants is a rule of `consultancy/domain`, which keeps the roles.
- **The user of a session is read through `consultancy`**, by the new `FindActiveUserByID`, as Between domain areas asks; `ActiveUser` grew instead of a second shape, so the login and the session read the same user. Both queries use a `LEFT JOIN`, so a user written with no role (only possible by hand) is still found, with no scope.
- **Authentication is a middleware of each operation that needs a user** (`restapi.RegisterForUser`), run before Huma reads the input: a request with nobody logged in gets 401 and its body is never judged. The 401 is `unauthorized`, the code named after its status, which ticket 05 reads as a session that ended. `AuthenticateWith` can come after the operations are registered.
- **The check of the origin lives in `platform/session`**, in `Under`, an `http.Handler` in front of every path under `/api`, rather than in a Huma middleware: it refuses before the session is read, covers every operation without an order of registration to keep, and lets the bounce webhook through by the rule itself, since it carries no cookie. It refuses every method but `GET`, `HEAD` and `OPTIONS` (the ticket names `POST` and `PUT`; `DELETE` and `PATCH` change state too). A client that sends neither header passes, as `curl` does.
- **Every refusal of a code looks the same.** A wrong code and the right code of a request ended, expired or used are each a wrong attempt, counted on the request until the third, which ends it. A browser with no request (an e-mail of no active user, no code asked for, a request that is gone) is answered by a stand-in request that never works, whose attempts the session keeps under `login_code_attempts` and asking again resets: otherwise the answer to typing a code would tell whether the e-mail belongs to a user.
- **One step logs a user in** (`LogIn`), with the way in finding its user inside the transaction (`FindUser`): it checks the user is active, records `logged_in` in the same transaction, and renews the session only after the commit, so a failure leaves no session holding a user who was not recorded. A right code of a user deactivated since they asked ends the request and answers `login_code_ended`; asking again sends nothing to a deactivated user.
- **The entry of a login** is acted by the user on themselves; the way in is a column of its own, `way_in`, whose CHECK says only that a login has one and nothing else does: the key of a provider is configuration, so the table cannot list it, and the domain checks its form.
- **Logging out needs no user**: it ends whatever session the browser has and answers 204, so the app always lands on the login with `logged_out`. It is not recorded.
- **The check answers 204** with the new cookie, and the app reads who is logged in with `GET /api/session`. A code that is not six digits fails the contract (`validation_failed` on `body.code`) and is no attempt.
- **`mountREST` returns an error** for a key of the login code too short, and the spec test passes a key of zeros: the use case holds the key from the start, as `LoginCodeContents` does.

### Found, and left for a decision

- **The time of a wrong code.** A browser with a request locks and updates its row; a browser with no request reads one row that does not exist and writes its session. The answers are the same; the difference in time, a statement or two, was not measured, as ticket 03 left the one of asking.
- **The other sessions of a deactivated user** end at their next request, when each is read; until then their rows stay in the table, and its cleanup removes them once they expire. Nothing ends them at the moment of the deactivation, which arrives with the use case that deactivates a user.
- **`role_keys` is an enum of the two keys of the setup.** A role a person creates will have a name and no key (ADR-0026), and this field changes then.
- **The development database is now at migration 24**, applied from this worktree for the check with `curl` before the merge; until the branch is merged, the API of another checkout on that database is not ready and its worker refuses to start (their newest migration is 23).

### Settled at the end of the effort

- **The time of a wrong code**: left as known, with nothing measured, as the maintainer decided for the login code. Recorded in ADR-0011.
- **The other sessions of a deactivated user end at their next request**: accepted by the maintainer. Recorded in ADR-0011 and in Session of Login in `CODING_STANDARDS.md`; the daily cleanup of the review-fix pass now removes them once they expire.
- **`role_keys` is an enum of the two keys of the setup**: accepted by the maintainer; it changes with the users effort. Recorded in ADR-0011 and in Operations of Login in `CODING_STANDARDS.md`.
- **The check of the origin refuses every method but GET, HEAD and OPTIONS, and lets a request with neither `Origin` nor `Sec-Fetch-Site` pass**: accepted by the maintainer. Recorded in ADR-0011 and in Sessions of API conventions. The review-fix pass reads `APP_ORIGIN` as a browser writes an origin (lowercase scheme and host, no default port) and compares the `Origin` read the same way.
- **The development database at migration 24**: no longer open.
